# 安全边界

英文兼容入口：`SECURITY.md`。

本文件是安全规则和敏感数据边界的中文主文档。安全规则优先级高于当前轮次状态、开发进展、项目交接和路线图。

## 安全硬约束摘要

- 明文 secret 不允许进入 SQLite / logs / frontend state / Wails events。
- password、明文 private-key content、passphrase、future token 和 proxy credential 都属于敏感数据。
- Key Vault 可以在 SQLite 中保存 Windows 当前用户级保护后的私钥密文，但不能保存明文私钥或口令。
- `SecretStore` 是 password / passphrase 的敏感信息边界。
- 前端只能看到 saved/available/sanitized reason code，不能接收真实 secret。
- 日志只能包含 sanitized lifecycle / error 信息，禁止 terminal input/output 和认证 payload。
- Backup / Export 的 secret 行为必须遵守当前加密备份安全边界。

# ServerPilot Security Model

## Sensitive Data

The following values are sensitive:

- passwords;
- plaintext private-key contents;
- private-key passphrases;
- future tokens and proxy credentials.

They must not be written to SQLite, JSON configuration, logs, source code,
generated frontend bindings, crash messages, analytics, or test snapshots.
The only SQLite exception is Key Vault's platform-protected private-key blob:
it is encrypted/protected by the backend before persistence, is never returned
to the frontend, and is not a portable plaintext secret.

## Non-Sensitive Alert History And Window State

Alert history may be stored in local SQLite only as sanitized, non-sensitive
event metadata:

- event ID, server ID, server-name snapshot, rule type, severity, source, and
  state;
- numeric current value, threshold, unit, started/resolved/read timestamps,
  session ID, and ended reason.

Alert history must not store IP addresses, usernames, credentials, Monitor raw
payloads, terminal input/output, command text, service logs, socket raw output,
private-key metadata beyond existing non-sensitive server references, or app
log bodies. Test alerts are not persisted. Alert mute state, pending evaluator
state, and live current metrics are memory-only.

Window state may store only local UI geometry: x/y/width/height, monitor
identifier, maximized state, restore bounds, layout version, and updated time.
It must not store server identifiers, credentials, terminal contents, command
history, file paths opened by SFTP editors, or remote system data.

`alert_history` and `window_state` are excluded from standard and full
Backup / Export payloads. They are local application state, not portable
configuration or secret material.

## Backup Password Rules

Encrypted backup and restore passwords must be handled as raw secret strings:

- minimum length is 6 Unicode characters;
- no uppercase, lowercase, digit, symbol, ASCII-only, or complexity rule is
  required;
- Chinese characters, spaces, symbols, digits, letters, and mixed Unicode
  input are allowed;
- leading and trailing spaces are part of the password and must not be trimmed;
- export, inspect, and import must use the exact same raw string;
- backup passwords must not be written to logs, SQLite, backup metadata, toast
  details, generated bindings, or app state snapshots.

## Credential Handling

Passwords and passphrases are provided for a test/connect operation and retained
only as long as required to construct an SSH authentication method. When the
user selects "remember", Windows stores the secret in Credential Manager.
SQLite stores only an opaque reference and the backend never returns the saved
secret to the frontend.

Monitoring, connection tests, terminals, and SFTP code must call the
same backend credential resolver. The frontend may query only booleans and
sanitized reason codes describing whether authentication can proceed; it never
receives a remembered password or passphrase. Missing references, unavailable
system secrets, invalid passphrases, and server-rejected saved credentials are
distinct states.

The add/edit form receives only the boolean `credentialSaved`; it never receives
the stored value. A blank edit preserves the current credential. An explicit
new value with Remember disabled deletes the previous stored credential. An
explicit Save may replace the credential immediately, while Save and connect
defers replacement until SSH authentication succeeds. System-store deletion
occurs before the SQLite reference is removed to avoid inaccessible orphaned
credentials.

A configured legacy private-key path may be stored because it is connection
metadata, but new Key Vault private-key servers should store a `key_vault_id`
instead of copying a path into the server profile.

Key Vault supports `legacy_file_path` and `encrypted_database` entries.
Legacy entries keep the old path-reference behavior until the user migrates
them. Encrypted entries store display name, source file name, algorithm,
public-key SHA-256 fingerprint, key bits, storage mode, protection version,
saved-passphrase boolean, notes, timestamps, usage count, and a
platform-protected private-key blob. On Windows that blob is protected with
DPAPI Current User scope and is bound to the Windows user that imported it.
SQLite must never contain PEM/OpenSSH private-key plaintext, passphrases,
SecretStore values, full original local paths for encrypted entries, or
decryption keys. The frontend may display metadata and source file name, but it
never receives private-key bytes or passphrases.

Key Vault passphrases use `SecretStore` keys in the format
`ServerPilot/keyvault/<keyID>/passphrase`. SQLite stores only the opaque
reference and `passphrase_saved`. Updating a saved passphrase first validates
the candidate against the decrypted encrypted entry or the legacy path entry;
a failed validation keeps the old SecretStore value. Deleting a key-vault
entry that is referenced by servers requires explicit user confirmation. The
backend must re-query real usage inside one SQLite transaction, clear every
matching server `key_vault_id`, and delete the key-vault row in that same
transaction. A database failure rolls back both the server reference clearing
and key deletion. After the transaction commits, ServerPilot attempts to delete
the corresponding SecretStore passphrase. SecretStore cleanup failure returns a
warning but does not restore the already deleted key row. Deleting a server
only removes server-owned credential references and never deletes the
key-vault entry.

After an in-use key-vault entry is deleted, affected server records remain
private-key / key-vault configurations with no selected key. Existing live SSH,
SFTP, monitor, tunnel, Docker, process, service, or network-detail sessions
must not be forcibly disconnected. Future credential resolution for those
servers must fail with a typed missing-key error until the user selects another
valid key. Legacy path key deletion removes only ServerPilot metadata and any
saved SecretStore passphrase reference; it must not delete, truncate, or modify
the user's original local private-key file.

`SecretStore` isolates platform behavior with build tags:

- Windows: Credential Manager implemented and tested;
- macOS: Keychain platform boundary retained for native implementation and
  macOS verification.

## Logging

Structured logs may contain:

- timestamp and severity;
- operation;
- connection ID;
- host and port;
- sanitized error classification;
- reconnect attempt and duration.

Logs must not contain authentication request objects, passwords, passphrases,
private-key bytes, complete environment dumps, or remote command output that
may contain secrets. Error wrapping must avoid embedding secret input.

Interactive terminal input and output are never written to the structured log.
Terminal logs are limited to sanitized lifecycle failures identified by
connection ID; they do not contain commands, screen contents, or PTY byte data.

## SFTP

SFTP uses an independent SSH client and `github.com/pkg/sftp.Client` per server
workspace. It reuses `credential.Resolver`, host-key policy, and Key Vault
metadata, but it never stores passwords, private-key bytes, passphrases, or
copied Key Vault secrets in its own state.

Allowed SFTP log and event data:

- server ID and operation name;
- sanitized error code and message;
- remote path or local path needed to explain the operation;
- transfer ID, byte counts, status, and speed.

Forbidden SFTP log and event data:

- file contents or file previews;
- passwords, passphrases, private-key bytes, or terminal input/output;
- complete large directory snapshots in application logs;
- generated backup data containing operating-system credential references as
  exportable secrets.

Uploads and downloads stream through fixed-size buffers. File contents are not
serialized through Wails JSON, written into SQLite, or written into structured
logs. Remote paths are handled with POSIX semantics; local paths are handled
with platform `filepath` semantics. This keeps Windows and macOS path handling
separate from remote Linux paths.

Remote text editing is the only current SFTP path allowed to return remote file
content to the frontend. It is user-initiated, limited to bounded UTF-8 text,
rejects binary-looking content and directories, and keeps the content only in
the active editor buffer. The backend must not log, persist, or include this
content in telemetry, transfer events, or error objects. Saves perform metadata
change checks before replacing the remote file.

Windows Explorer drag/drop upload uses Wails file-drop absolute paths. The
frontend passes paths into backend upload APIs and does not read browser
`File` contents, synthesize paths, or serialize upload bytes through Wails JSON.

The CodeMirror remote editor is still subject to the same bounded text-editing
rules. Search terms, editor buffers, cursor positions, and unsaved content are
frontend memory state only. They must not be written to structured logs,
SQLite, localStorage, generated bindings, or crash reports. Dirty-close
decisions use the application dialog host; browser-native prompts are not used.

SFTP text-save diagnostics may record metadata only: server ID, remote path,
save stage, size, mtime, permission bits, and sanitized technical errors.
They must not include file contents, editor buffers, selected text, search
terms, passwords, private-key material, or passphrases. The staged JSON save
error returned to the frontend follows the same metadata-only rule.

The direct-write fallback for text saves is deliberately bounded. It is used
only after the target file has been statted as an existing non-directory and
the temporary-file replacement path fails. It opens the existing target with
write/truncate flags and never removes the original target before a successful
write. External modification conflicts still require explicit overwrite
confirmation from the user.

Upload completion refresh uses transfer metadata only: connection ID, transfer
direction/status, final remote path, and parent directory. It never reads or
logs uploaded file contents and does not create new SFTP sessions to refresh
the listing.

SCP fallback for SFTP-less hosts is implemented as an SFTP-manager-owned
compatibility path with its own SSH transport. It must not reuse the SSH
terminal session or introduce a new SSH reuse model. Single-file transfers use
legacy SCP command sessions, while recursive transfers use shell compatibility
listing/mkdir plus per-file single-file SCP instead of `scp -r`.

Because SCP compatibility constructs POSIX shell commands, it must use the
shared quoting helper for every remote path argument. Remote paths must reject
parent traversal, root targets, and reserved paths. Shell listing parsers must
reject unsafe entry names containing path separators, NUL, CR/LF, `.`, or
`..`. Local recursive downloads must keep every target inside the selected
local root and reject symlink path escape. File contents must continue to
stream through backend file/SCP pipes only and must not enter Wails JSON,
SQLite, logs, backup/export, command history, or persisted frontend state.

The SFTP status-bar transfer summary and transfer popover display metadata
only: direction, file name, progress, byte counts, speed, status, and sanitized
failure text. They do not display file contents, previews, passwords,
passphrases, private-key bytes, or terminal input/output. The right-side SFTP
details panel is metadata-only and uses listed SFTP entry fields such as name,
type, size, permissions, owner, group, modified time, hidden status, symlink
status, and remote path.

Automatic SFTP opening after SSH terminal connection reuses the existing
credential-resolution path. If a temporary password or passphrase was supplied
for the SSH terminal, it may be reused in memory for the automatic SFTP open.
If no reusable authentication context exists, the UI marks SFTP as requiring
credentials instead of creating repeated authentication dialogs. No temporary
secret is written to local storage, SQLite, logs, or generated bindings.

## Command History And Favorites

Command history records only submitted terminal command lines. It must not
record terminal output, stdout/stderr, ANSI buffers, unsubmitted input, SFTP
file contents, remote editor contents, passwords, passphrases, private-key
contents, or prompts and responses used for authentication.

The frontend skips the next submitted line after a password/passphrase-looking
terminal prompt. The backend also filters empty commands, control sequences,
multi-line paste content, commands longer than 1000 characters, and common
secret-bearing patterns such as `password=`, `passwd=`, `pass=`, `token=`,
`secret=`, `api_key=`, `apikey=`, `Authorization:`, `PRIVATE KEY`,
`sshpass -p`, `mysql -p...`, and `curl -u user:password`.

Filtered history commands are not written to SQLite, logs, localStorage,
backup files, or frontend persisted storage. The UI may show a generic toast
that a command was skipped, but it must not show the skipped command text.

Favorites may contain commands only after explicit user entry. Suspicious
favorite commands require a confirmation dialog before saving. Favorites are
not exported by standard or full backup.

## SSH

- Use `golang.org/x/crypto/ssh`.
- Require host-key handling through the typed `auto_update` or `strict`
  policy.
- `auto_update` is the default. Unknown and changed host fingerprints do not
  block connection, but the observed SHA-256 fingerprint may be saved or
  replaced only after SSH authentication and client creation succeed.
- `auto_update` lowers detection of host identity mismatch and therefore
  reduces middle-person attack resistance compared with `strict`.
- `strict` blocks unknown and changed host fingerprints until the user confirms
  a trust/update action. The confirmation UI may display saved and observed
  SHA-256 fingerprints only.
- Never use `ssh.InsecureIgnoreHostKey`.
- Store only the SHA-256 fingerprint per connection; never log or persist raw
  host public keys.
- A separate strict-mode trust action must re-probe the current fingerprint
  before saving and must not accept arbitrary raw host-key material from the
  frontend.
- Apply dial, handshake, and command timeouts.
- Close clients and sessions on cancellation.
- Do not implement cryptographic primitives or SSH framing.

## Local Storage

- Use a pure Go SQLite driver with `CGO_ENABLED=0`.
- Store the database under the operating system's user configuration directory.
- Use parameterized SQL and transactional migrations.
- Restrict file permissions where the host platform supports it.
- Do not store application secrets in preferences or migration defaults.
- SQLite may store Key Vault protected private-key blobs only through the
  platform protector. It must not store plaintext private keys, passphrases,
  protector master keys, or DPAPI unprotected material.
- Standard backups must not export Key Vault passphrase references, protected
  private-key blobs, or operating-system secrets. Full backups may export
  SecretStore values only inside the encrypted backup payload and never export
  the SecretStore keys themselves; they still do not export protected blobs.

## Backup Files

ServerPilot backup files are encrypted `.spbackup` files. The outer JSON
envelope may contain only backup format/version, creation time, application
name, Argon2id parameters, random salt, XChaCha20-Poly1305 parameters, random
nonce, and ciphertext. Business data such as server names, hosts, usernames,
private-key paths, Key Vault names, and host trust records must not appear in
the envelope as plaintext.

The backup password exists only in memory for the current export, inspect, or
import operation. It is never written to SQLite, localStorage, SecretStore,
logs, generated bindings, or configuration files.

Standard backups may include non-sensitive migratable metadata:

- application settings suitable for migration;
- groups;
- server connection metadata;
- Key Vault metadata for local rebind by fingerprint;
- host-key trust metadata when the user imports it.

Standard backups must not include:

- Windows Credential Manager values;
- macOS Keychain values;
- SecretStore keys or credential references;
- passwords;
- private-key passphrases;
- private-key file contents;
- Key Vault protected private-key blobs;
- remote file contents;
- terminal input/output;
- logs;
- SFTP transfer history;
- open workspace or terminal state.

Full backups are opt-in and require the same backup password plus a second
confirmation in the UI. They may include saved SecretStore values such as SSH
passwords, local private-key passphrases, and Key Vault passphrases inside the
encrypted payload only. Full backups still must not include SecretStore keys,
credential references, private-key file contents, Key Vault protected blobs,
remote file contents, terminal input/output, logs, SFTP transfer history, or
workspace state. Cross-computer encrypted Key Vault material export/import is
a separate future feature and is not silently enabled by full backup.

Command history, command favorites, and command completion suggestions are
excluded from both standard and full backups. Completion suggestions are
derived from existing history/favorites plus static builtin templates at
runtime. Builtin templates are never stored in SQLite. Completion must not
export, persist, or display terminal output, unsubmitted input, passwords,
private-key contents, passphrases, remote editor buffers, or SFTP file
contents.

Standard import clears credential state. Imported password connections do not
show a saved password. Imported local-key or Key Vault connections do not show
a saved passphrase. Imported Key Vault metadata is rebound to an existing local
entry by fingerprint when possible. Missing local keys are imported without a
stale `key_vault_id` and must be selected or imported by the user. Backup
import must not clear the current machine's Key Vault. Full import restores
mapped SecretStore values after metadata import and then writes new local
credential references.

Host-key trust import is explicit. After import, later fingerprint changes
follow the current SSH host-key policy: `auto_update` updates after successful
SSH authentication, while `strict` blocks until explicit trust/update.

Wrong passwords, tampered ciphertext, tampered nonce/salt, unsupported backup
versions, invalid KDF parameters, and invalid payload structures must fail
before import. Database import is transactional, so a failed import rolls back
the attempted changes.

## Frontend Boundary

Typed Wails methods receive secrets only in dedicated transient authentication
fields. Pinia must not persist authentication requests to localStorage. UI
errors must be sanitized and must not render raw private-key data.

The terminal completion frontend keeps only an in-memory per-session line
buffer for safety decisions. If the buffer becomes dirty because of control
sequences, multiline paste, cursor movement, or alternate-screen programs, the
completion overlay refuses to write suggested bytes. Sensitive prefixes such
as `password=`, `token=`, `Authorization:`, `sshpass -p`, `mysql -p...`, and
`curl -u user:password` are skipped without echoing the original text in logs
or toast details.

Local terminal input, output, shell history, environment variables, current
working directory history, terminal buffer, ANSI output, and command content
must not be written to SQLite, logs, backup files, localStorage, or long-lived
Wails caches. Local terminal output events carry base64 payloads only for
runtime rendering in xterm.js and are not logged. The backend may log sanitized
local terminal lifecycle events and error categories, but not environment
values, command lines, input bytes, or output bytes.

Local terminal is not a server runtime and must not use server IDs. It must not
participate in `DisconnectServer(serverID)`, monitor collection, SFTP, SSH
credential resolution, Key Vault, command history, command favorites, command
completion, backup, import, or export.

## Threats Deferred Beyond MVP

- macOS native Keychain persistence;
- signed application releases and notarization;
- enterprise policy enforcement;
- hardware-backed keys and SSH agents;
- encrypted database fields;
- audit export and retention policies.

Deferred items must not be represented in the UI as completed security
features.
